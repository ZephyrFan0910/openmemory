🔴 严重 Bug（会导致数据错误）
1. ingest.js 调用了不存在的函数 insertEntity
js// ingest.js 第 63 行
const dbEntity = insertEntity(db, { ... });
但顶部 import 是：
jsimport { insertEntities, indexEntityForChunk, getEntityByName } from '../store/entities.js';
insertEntity（单数）没有被 import，insertEntities（复数）才是。这会在有实体的 chunk 入库时直接抛 ReferenceError，整个摄入管线会崩。
修复：把 import 里的 insertEntities 改成 insertEntity，或把调用改成 insertEntities(db, [entity])[0]。

2. seal.js 的 tokenCount 用的是字符长度而不是 token 数
js// seal.js 第 76 行
insertTreeNode(db, {
  ...
  tokenCount: summaryContent.length,  // ❌ 这是字符数，不是 token 数
摘要节点的 tokenCount 用 summaryContent.length 赋值，但 L0 叶子节点用的是 chunk.token_count（正确的 token 估算值）。这导致上层节点的 token 统计完全混乱，shouldSeal 在 L1+ 虽然只看条目数不看 token，但 getTreeStats 和你将来做 token 预算管理时会出问题。
修复：
jstokenCount: estimateTokenCount(summaryContent),

🟡 中等 Bug（功能受损但不崩溃）
3. buildTree 的 forceRebuild 只清了一张表
jsif (forceRebuild) {
  db.prepare('DELETE FROM tree_nodes').run();  // ✅
  deleteBuffersForTree(db, treeId);            // ✅
  // ❌ 缺少: 没有清 chunks 的 lifecycle 字段
}
重建后旧 chunks 的 lifecycle 还是 'sealed' 或 'built'，但重建会重新 ingest 它们，lifecycle 状态就不一致了。如果你将来用 lifecycle 过滤查询会出现奇怪结果。
修复：在 forceRebuild 里加：
jsdb.prepare("UPDATE chunks SET lifecycle = 'scored' WHERE lifecycle IN ('built','sealed')").run();

4. sealAllPending 的终止条件有逻辑问题
js// seal.js
for (let level = 0; level < MAX_CASCADE_DEPTH; level++) {
  const buf = getBuffer(db, treeId, level);
  if (!buf || buf.item_ids.length === 0) break;  // ❌ 跳过了中间空层
  if (shouldSeal(buf, level)) { ... }
  else { break; }  // ❌ 不密封就直接退出，上层可能还有待处理的
}
如果 L1 的 buffer 为空但 L2 有积压，会直接 break 不处理 L2。这在正常流式导入时不会触发，但 buildTree 的批量场景或者边界情况下可能漏掉上层节点。

🟢 轻微问题（不影响功能，但值得注意）
5. db.js 是模块级单例，测试时会有副作用
_db 是模块级变量，如果你以后写测试，多个测试用例会共享同一个连接，导致测试间相互污染。现在不用管，但以后写测试时要注意。

6. searchChunks 的 FTS 查询对中文不友好
jsWHERE chunks_fts MATCH ?
FTS5 默认用空格分词，中文没有空格，查"项目架构"其实是在找整个短语，而不是"项目"和"架构"分别匹配。效果会比预期差。短期可以在查询词里手动加空格拆开，中长期需要接 jieba。
